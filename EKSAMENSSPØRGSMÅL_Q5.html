Hvad er en Message Channel?

En message channel er et abstraktionslag til at flytte beskeder mellem komponenter. Channels kan være point-to-point (queue), publish-subscribe (topic) eller streams (event log).

Kan implementeres via brokers som RabbitMQ (queues, exchanges), Kafka (partitions, topics) eller enklere HTTP end-points.

Typer af Message Channels

Channel typeBeskrivelseEksempler
Point-to-Point / QueueEn besked leveres til én consumer (work queue)RabbitMQ queue, SQS
Publish-Subscribe / TopicProducent publicerer til topic; mange consumers kan abonnereRabbitMQ fanout/topic exchanges, MQTT topics
Event Stream / LogUendelig append-only log; consumers læser fra offsetKafka topics, Kinesis
Request-ReplySynkron-lignende mønster over messaging (correlation id)RPC-over-message, temporary reply queue

Repo-eksempel: Exchange + topic i projektet

I vores projekt deklareres en topic-exchange i Storage microservice:

RabbitMQModule.forRoot({
  exchanges: [{ name: 'catalog_item_stock.exchange', type: 'topic' }],
  uri: process.env.RABBITMQ_URI || 'amqp://guest:guest@localhost:5672',
});

Dette betyder at services publicerer til exchange-navnet og bruger routing keys som f.eks. catalog_item_stock.reserve eller catalog_item_stock.confirm.

Synkron vs Asynkron kommunikation

Synkron

Producer venter på svar fra consumer (fx HTTP REST). Simpelt flow, nem fejlhåndtering, men tight coupling og lavere resilience.

Asynkron

Producer sender besked og fortsætter; consumer håndterer beskeden senere. Øger decoupling og resilience, men introducerer eventual consistency og kompleksitet (idempotency, ordering).

Valg påvirker transaktionalitet, latency, fejlhåndtering og hvordan du tester integrationen.

Hvordan valget påvirker integration

  • Latency og brugeroplevelse: synkron er hurtig og simpel for realtime svar; asynkron tillader baggrundsbehandling.
  • Fejlhåndtering: asynkron kræver DLQ, retry-strategier og overvågning.
  • Data consistency: asynkron → eventual consistency; design kompensation og tilstandsovervågning.
  • Skalering: asynkron gør det muligt at skrue op for consumers uafhængigt af producenter.

Messaging-mønstre i Microservices

  • Event-driven architecture: services emitter events for state changes
  • Command messaging: sende en kommando til en ansvarlig service (ofte queue)
  • Pipes & Filters: kæd små services som transformere via messages
  • Saga: orkestrer langvarige transaktioner over flere services
  • Request-Reply over messaging: brug correlation-id for at linke svar

Repo-eksempel: Consumer + RPC

Storage-microservicen bruger både subscribe og RPC handlers (NestJS):

@RabbitSubscribe({
  exchange: 'catalog_item_stock.exchange',
  routingKey: 'catalog_item_stock.restock',
  queue: 'catalog_item_stock_restock_queue',
})
async handleRestock(msg: DefaultDTOItem[]) { /* ... */ }

@RabbitRPC({
  exchange: 'catalog_item_stock.exchange',
  routingKey: 'catalog_item_stock.reserve',
  queue: 'catalog_item_stock_reserve_rpc_queue',
})
async handleReserveRpc(msg: DefaultDTOItem[]) { /* ... */ }

Forklaring: RPC bruges når caller forventer et svar (fx reservation check), mens subscribe er for events.

Praktisk: hvordan vi kan bruge messaging i semesterprojektet

  • Brug events til at notify andre services (fx OrderPlaced -> InventoryService, BillingService)
  • Implementér en event bus med RabbitMQ for relay og routing (exchanges + bindings)
  • Brug Kafka til højt throughput/ordering-krav

Repo-eksempel: Python publisher i Order Service

# MicroServices/OrderMicroService/order-service/app/events.py
async def publish(self, routing_key: str, payload: dict):
    if self.connection is None or self.connection.is_closed:
        await self.connect()
    body = json.dumps(payload).encode()
    message = Message(body, content_type='application/json', delivery_mode=2)
    await self.exchange.publish(message, routing_key)

I services.py oprettes events asynkront, så HTTP-API'en ikke blokeres:

# MicroServices/OrderMicroService/order-service/app/services.py
asyncio.create_task(safe_publish('catalog_item_stock.confirm', confirm_payload))

Delivery mode 2 + durable exchanges/queues sikrer persistence ved broker genstart.

Reliability: levering og garantier

  • At most once — mulig data tab ved netværksfejl
  • At least once — kan give duplikater; kræver idempotency
  • Exactly once — svært og ofte dyrt; iblandt opnået via stream processing og commit-log

Vælg leveringsgaranti baseret på use-case — idempotency er ofte en god investering.

Repo-eksempel: persistent messages

Order-service sætter delivery_mode=2 ved oprettelse af Message(..., delivery_mode=2) og exchange deklareres durable — dette giver persistence over broker genstart.

Skalering & partitioning

Til højt throughput brug partitioning (Kafka partitions) eller flere consumers i samme consumer-group. Vær opmærksom på ordering indenfor partitioner.

Operational concerns

  • Monitoring: track lag (Kafka), queue depth (RabbitMQ)
  • Alerting: DLQ growth, consumer errors, retry storms
  • Schema evolution: backward/forward compatible changes
  • Security: authenticate/authorize producers and consumers

Implementerings-tips

  • Design events som facts, ikke commands (separation af ansvar)
  • Brug metadata (schema_version, event_id, correlation_id, timestamp)
  • Implementér idempotency keys for handlers
  • Hold beskeder små og parseable
