Spørgsmål 6 — Domæneopdeling og Messaging Patterns

Lang præsentation (10–15+ minutter). Fokus: hvordan identificere servicegrænser, migrationsteknikker og anvendelse af message routing i integration.

Agenda & tidsfordeling

  • 1 min — Introduktion: hvorfor opdele
  • 3 min — Strategier: incremental migration, decomposition by layer, strangler fig
  • 4 min — Hvordan identificere domæner / bounded contexts
  • 3 min — Prioritering og risikostyring
  • 4 min — Messaging patterns: Message Routing & praktisk anvendelse
  • 2–3 min — Opsummering & anbefalinger

Hvorfor opdele en monolit?

  • Skalerbarhed: mulighed for at skalere kritiske komponenter separat
  • Fleksibilitet: forskellige teams kan eje services uafhængigt
  • Udrulning: hurtigere, mindre risikofyldte deploys
  • Teknologivalg: hvert service kan bruge sin optimale tech stack
Men opdeling øger kompleksitet i drift, integration og data consistency — derfor planlægning er nødvendig.

Strategier for migration og opdeling

Incremental migration / Strangler Fig

Gradvis erstatning: læg ny funktionalitet i services, redirect trafik fra monolit til nye services, trinvise ekstraktioner.

Decomposition by Layer

Opdel efter tekniske lag (UI, API, business logic, data). Kan være en god start, men mindre effektiv end domain-driven decomposition for forretningsmodeller.

Decomposition by Business Capability / Domain

Find bounded contexts (Orders, Inventory, Billing). Dette er ofte den mest holdbare: høj kohæsion indenfor service, lav kobling mellem services.

Hvordan identificere og prioritere domæner

  • Analyser forretningskapabiliteter: hvilke funktioner ændres ofte?
  • Coupling vs Cohesion: find tætte kluster af klasser/tabeller/metoder med høj indbyrdes afhængighed
  • Operational requirements: hvilke komponenter kræver separat skalering eller isoleret sikkerhed?
  • Team boundaries: hvem ejer funktionaliteten? Reorganisér services efter teams for effektivt ejerskab

Konkrete trin (praktisk)

  1. Log and measure: find hotspots (latency, deployment frequency, change-rate)
  2. Identify candidate bounded contexts via domain events and data ownership
  3. Prototype extraction of a read-only slice (thin anti-corruption layer)
  4. Incrementally move write-paths once read-path is stable

Prioritering og risikostyring

Prioritér efter business value, risikominimering og lav teknisk gæld. Eksempler på høj-prioritet services:

  • Services med høj trafik eller store portioner af responstid
  • Forretningskritiske flows (checkout, payment)
  • Komplekse domæner med hyppige ændringer
Lav en plan for rollback, integrationstest og kontrakt-gates før hver ekstraktion.

Messaging Patterns — Message Routing

Message Routing sørger for at beskeder bliver leveret til relevante services uden tight coupling. Typiske routing-typer: topic routing (routing keys), header-based routing, content-based routing (message broker eller dedicated router).

Praktisk: routing keys og exchanges

Convention: {domain}.{entity}.{action}, fx orders.created eller catalog_item_stock.reservation.expired.

Repo-eksempel: exchange + routing keys

// Storage microservice (NestJS)
RabbitMQModule.forRoot({
  exchanges: [{ name: 'catalog_item_stock.exchange', type: 'topic' }]
});

// Publisher
await this.amqpConnection.publish('catalog_item_stock.exchange', 'catalog_item_stock.reserve.success', payload);

// Consumer binding
@RabbitSubscribe({ exchange: 'catalog_item_stock.exchange', routingKey: 'catalog_item_stock.confirm', queue: 'catalog_item_stock_confirm_queue' })
async handleConfirm(msg) { /* ... */ }

Hvorfor Message Routing hjælper ved opdeling

  • Decoupling: services kender ikke hinandens endpoints — kun events
  • Selective subscription: consumers vælger relevante routing keys
  • Evolution: nye services kan subscribes uden producer-ændringer
  • Operational: mulighed for retries, DLQ og traffic shaping ved broker

Integration-tilgang i praksis (trinvise eksempler)

  1. Extract read model: lav en service der læser fra monolitens DB (read-only) og publicerer events fra den nye service.
  2. Introduce anti-corruption layer (ACL): adaptér monolitens formater til nye service-interfaces.
  3. Move write-paths gradually: begynd med lav-risk funktioner, vær omhyggelig med contracts.
  4. Use event-driven integration: producer events fra nye services og få monolit/andre services til at subscribes.

Repo-relateret eksempel

I projektet kan Order Service publicere catalog_item_stock.confirm event (se MicroServices/OrderMicroService/order-service/app/services.py), og Storage Service lytter og udfører reservation/confirm logik (se MicroServices/storage-micro-service/src/stock/catalog-item-stock.consumer.ts).

Governance: contracts, schema registry, versioning

  • Brug schema version i events (fx schema_version)
  • Contract tests (Pact) som CI-gate mellem producer og consumer
  • Backward/forward compatibility regler

Opsummering & anbefalinger

  • Start small: extract read paths og build trust
  • Prioritér efter business value og risiko
  • Brug message routing for loose coupling og fleksibel integration
  • Investér i contracts, observability og retries/DLQ
