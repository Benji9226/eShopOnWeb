Testtyper — kort

Unit tests

Tester en enkelt funktion eller klasse isoleret. Hurtige, deterministiske. Bruges til at sikre korrekthed af små enheder — fx validering, mapping eller transformation-funktioner.

Key: Hold unit tests små og hurtige; mock eksterne afhængigheder.

Integration tests

Tester samspillet mellem komponenter (fx repository ↔ database, service ↔ broker). Brug ephemeral resources (SQLite, Testcontainers eller lightweight docker-compose) så tests er realistiske men reproducible.

Key: Verificer contracts og dataflow — brug faktiske netværkskald mod containeriserede dependency-mocks.

End-to-end (E2E)

Tester hele flowet fra klient til persistence for at sikre business-funktionalitet. Tungere og køres typisk sjældnere (nightly eller gated runs).

Struktur i semesterprojekt

Praktisk strategi i et multi-service projekt:

  • Hver service ejer sine unit tests (kør ofte lokalt).
  • Integration tests køres i CI (brug test-DB eller ephemeral containers — Testcontainers anbefales).
  • E2E tests kører i trimmed Docker Compose eller separat testmiljø.
Eksempler i repo: Python pytest fixtures i MicroServices/CatalogMicroService/tests/conftest.py, xUnit i eShopOnWeb-main/.../tests/UnitTests, Jest for NestJS i storage-micro-service.

Concrete repo-eksempler

  • CatalogMicroService (Python) — MicroServices/CatalogMicroService/tests/conftest.py opretter en test-SQLite eller bruger Testcontainers; kør pytest. Fixture-eksempel: database-seeding og transactional rollback.
  • OrderMicroService (Python) — lignende mønstre; brug fixtures til at mocke eksterne APIs og ephemeral RabbitMQ.
  • Storage (NestJS) — kør npm test (Jest); mock services med dependency injection for hurtige unit tests.
  • .NET — dotnet test i tests/UnitTests; integration mod SQL Edge eller containeriseret SQL i CI.
CI: se .github/workflows/build-and-test.yml — kører test-suites og bygger Docker-billeder. Brug miljøvariabler og secrets for credentials i CI.

Hvad er Message Transformation?

Message Transformation ændrer et message-format for at gøre det kompatibelt mellem systemer. Typiske transformationer:

  • Feltnavn konvertering (camelCase ↔ snake_case).
  • Schema-opgradering (v1 → v2) med migrering af felter.
  • Berigelse (tilføj metadata) eller redigering (fjern interne felter).
I eShopOnWeb kan et OrderCreatedEvent indeholde interne felter; en transformer kan fjerne disse før consumer-evaluering for at mindske coupling.
Tip: Hold transformationslogikken testbar som rene funktioner (enkelt ansvar) så unit tests nemt kan validere mappings.

Hvor placere transformation?

  • Producer-side: Producer sender consumer-friendly format — enkelt at versionere, men kræver producent-ansvar.
  • Broker-side / middleware: Gateway eller dedikeret transformer-service (centraliseret og genbrugeligt).
  • Consumer-side: Consumer transformerer lokalt — fleksibelt, men kan føre til duplikation.
Overvej ownership, performance og hvor ofte skemaer ændres. Til hyppige ændringer kan middleware være fordelagtigt.

Teststrategier for messaging

  1. Unit tests: Test transformationslogik isoleret (f.eks. transform_v1_to_v2(payload)). Mock broker-klienten.
  2. Integration tests: Brug ephemeral RabbitMQ (Docker/Testcontainers) for at verificere publish/consume og transformation i en pipeline.
  3. Contract tests: Consumer-driven contracts (Pact eller schema registry) sikrer kompatibilitet mellem producenter og forbrugere.
  4. E2E: Kør hele flow (API → publish → transform → consume → DB) og valider end-state i en isoleret testmiljø.
Forslag: Kør integrationstest i CI som en separat job, brug retries/cleanup for flakiness, og gem relevante logs for debugging.

Eksempeltest — Messaging integration (pseudo)

# pseudo pytest
def test_order_event_transformation(rabbitmq_container):
    # arrange
    publish(queue='orders.in', body=ORDER_V1_JSON)

    # act
    msg = consume(queue='orders.out', timeout=5)

    # assert
    assert msg['amount'] == 1000
    assert 'internal_flag' not in msg  # fjernet af transformer
    assert msg['schema_version'] == 'v2'

Flow: start ephemeral broker (docker) → publish → transformer-service/process → consume → assert end-state i test.

Råd: Brug idempotent publish og clean-up mellem tests; kør med korte timeouts og giv gode fejl-logs.

Test automation & CI

Praksis:

  • Unit tests: Kør lokalt og i pre-commit (hurtig feedback).
  • Integration tests: Kør i CI med containerized dependencies (se .github/workflows/build-and-test.yml).
  • E2E: Kør nightly eller som gating for store merges.
  • Contract tests: Kør i både consumer- og producer-repos; bryd ikke contracts uden versionsstrategi.

Tip: Del integration tests i hurtige vs. langsomme job; brug artefakter til at samle logs fra flakede tests.

Opsummering & Best Practices

  • Unit tests for correctness (hurtige).
  • Integration tests for contracts og transformations.
  • E2E for kritiske business flows.
  • Brug contract testing (Pact) for kompatibilitet.
  • Test messaging med ephemeral brokers (Docker / Testcontainers) og valider DLQ-behandling.
Takeaway: Gør transformationslogik small, testbar og versioneret; automatiser integrationstests i CI for at fange regressions tidligt.
