🔴 Slide 1: Testtyper — hurtig oversigt

Unit tests

Isolerede tests af en enkelt funktion eller klasse. Hurtige og deterministiske. I kontekst af message transformation betyder det: test at en given input JSON konverteres korrekt til ønsket output (mapping, feltnavn, datatyper).

Integration tests

Tester samspil mellem to eller flere komponenter, fx en transformer-funktion + en serializer + en broker klient. Ofte kører de mod ephemeral afhængigheder (SQLite, RabbitMQ i Docker eller Testcontainers).

End-to-end (E2E)

Tester hele forretningsflowet fra API → publish → consume → DB. Langsommere, men sikrer at alle dele spiller sammen.

🔎 Slide 2: Hvorfor vælge flere lag af tests?

Hver testtype fanger forskellige fejl: unit fanger logikfejl hurtigt, integration fanger fejl i afhængighedsopsætning, E2E fanger samspilsfejl. Kombinationen giver tillid uden at gøre udviklerfeedback for langsom.

Praktisk anbefaling: 70% unit, 25% integration, 5% E2E i test-suites, justér efter projektets kompleksitet.

🧭 Slide 3: Valg af scope i semesterprojekt

I et multi-service projekt er det ikke realistisk at skrive fulde E2E-suiter for alt. Prioritér:

  • Core business flows som E2E (fx checkout/order flow)
  • Transformationslogik og contracts som både unit og integration
  • Fejl-/poison-message flows og DLQ som integration eller E2E

Eksempel: Test transform_v1_to_v2 som unit; test publish → transform → consume som integration mod ephemeral RabbitMQ.

🔧 Slide 4: Implementationsmønstre & hvor i repoet

Kort gennemgang af konkrete mønstre i koden og hvor du finder dem — præsenteret som "problem → løsning → hvor i repoet".

1) Publisher / Subscriber (event-driven)

Problem: Flere services skal reagere på en ordre uden direkte HTTP-kald.

Løsning: Publish events til en exchange; services subscribes via routing keys.

Hvor: MicroServices/OrderMicroService/order-service/app/events.py (publisher) og MicroServices/storage-micro-service/src/stock/catalog-item-stock.consumer.ts (consumer).

# events.py (publisher)
await self.exchange.publish(message, routing_key)

// consumer (NestJS)
@RabbitSubscribe({ exchange: 'catalog_item_stock.exchange', routingKey: 'catalog_item_stock.confirm', queue: '...'} )
async handleConfirm(msg) { /* ... */ }

2) RPC over messaging (request-reply)

Problem: Nogle kald kræver direkte svar (fx reservation check).

Løsning: RPC pattern med temporary reply queues eller @RabbitRPC i NestJS.

Hvor: MicroServices/storage-micro-service/src/stock/catalog-item-stock.consumer.ts (se @RabbitRPC handlers).

3) Background jobs & cron publishing

Problem: Periodisk oprydning eller tidsbaserede events (fx udløbne reservationer).

Løsning: Cron-job der opdaterer DB og publicerer batch-events.

Hvor: MicroServices/storage-micro-service/src/stock/cron/reservation-cleanup-cron.service.ts

4) Test fixtures & integration patterns

Problem: Integrationstests har brug for isolerede databaser og brokers.

Løsning: pytest fixtures / jest mocks + ephemeral RabbitMQ i Docker/Testcontainers.

Hvor: MicroServices/CatalogMicroService/tests/conftest.py og MicroServices/storage-micro-service/src/__tests__/catalog-item-stock.service.spec.ts

# jest test (mock AmqpConnection)
mockAmqp = { publish: jest.fn().mockResolvedValue(undefined) };
expect(mockAmqp.publish).toHaveBeenCalledWith('catalog_item_stock.exchange', 'catalog_item_stock.reserve.success', expectedResults);

5) CI integration

Problem: Kørsel af unit + integration tests og bygning af images.

Løsning: Separate CI jobs (unit / integration / e2e) i GitHub Actions.

Hvor: .github/workflows/build-and-test.yml — se job-opdeling og test-artefakter.

Tip: Når du præsenterer, peg hurtigt på ét problem → vis den løsning koden indeholder → nævn filplacering for hurtig opfølgning.

🔁 Slide 5: Hvad er Message Transformation?

Message Transformation ændrer payload mellem producer og consumer: feltnavn-ændringer (camelCase ↔ snake_case), skema-opgraderinger (v1 → v2), eller berigelse (tilføj metadata).

Hvorfor?

  • Backward compatibility: Nye services kan acceptere gamle events
  • Separation of concerns: Producer holder interne felter private
  • Versionstyring: Muliggør evolution af events uden at bryde konsumenter

🧪 Slide 6: Unit-test af en transformer (eksempel)

# pseudo Python unit test (pytest)
def test_transform_v1_to_v2():
    input_v1 = {
        "orderId": 123,
        "userId": 456,
        "amount": 1000,
        "internal_flag": True
    }

    expected_v2 = {
        "order_id": 123,
        "user_id": 456,
        "amount_cents": 100000,
        "schema_version": "v2"
    }

    result = transform_v1_to_v2(input_v1)
    assert result == expected_v2

Placér sådan test ved siden af implementationsfilen (samme modul), så refactorer-detection er nem.

🔌 Slide 7: Integrationstest med ephemeral RabbitMQ

Brug Docker Compose eller Testcontainers for at starte en midlertidig RabbitMQ instance, publish en event og consume den fra transformer/consumer pipeline.

# pseudo pytest med fixture rabbitmq_container
def test_publish_and_consume_transform(rabbitmq_container):
    publish_json('orders.in', ORDER_V1_JSON)
    msg = consume_json('orders.out', timeout=5)
    assert msg['schema_version'] == 'v2'
    assert 'internal_flag' not in msg

I repoet kan du se patterns i MicroServices/*/tests hvor fixtures håndterer start/stop og cleanup.

🔐 Slide 8: Contract testing (Consumer-Driven Contracts)

Brug Pact eller et schema registry for at dokumentere forventninger mellem producer og consumer. Contract tests kører i både consumer- og producer-repo for at sikre kompatibilitet før deploy.

Fordel: Catch breaking changes tidligt uden at køre fuld integrationstack.

⚙️ Slide 9: CI-patterns - hvordan vi kører tests

Eksempel på opdeling i CI (se .github/workflows/build-and-test.yml):

  1. Job: install & run unit tests (parallel per service)
  2. Job: integration tests (start ephemeral services via docker compose / testcontainers)
  3. Job: e2e (trimmet miljø eller nightly)
# typisk CI-kommando (PowerShell / Windows)
python -m venv venv
.\venv\Scripts\activate
pip install -r requirements.txt
pytest -q

dotnet test ./eShopOnWeb-main/eShopOnWeb-main/tests/UnitTests/UnitTests.csproj
Gem logs og RabbitMQ messages som artefakter for hurtig debugging ved fejl.

🛠️ Slide 10: Test for fejlhåndtering (DLQ & retries)

Test at poison messages ender i DLQ og at operator kan reprocessere dem. Simuler en bug i consumer og verificer at message når orders.dlx efter X retries.

# pseudo
def test_poison_message_goes_to_dlx(rabbitmq_container):
    publish_bad_message('orders.in')
    assert wait_for_message('orders.dlx', timeout=10)

💡 Slide 13: Best practices

  • Skriv transformationslogik som rene, testbare funktioner.
  • Brug ephemeral services i integration tests for stabilitet.
  • Automatiser contract tests i CI.
  • Test DLQ flows og monitor retry-metrics.
