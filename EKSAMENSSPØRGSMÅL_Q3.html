Slide 1: Testtyper kort

Unit tests

Tester en enkelt funktion eller klasse isoleret. Hurtige, deterministiske. Bruges til at sikre korrekthed af små enheder.

Integration tests

Tester samspillet mellem komponenter (fx repository ↔ database, service ↔ broker). Bruger ofte letvægts test-DB eller containeriserede afhængigheder.

End-to-end (E2E)

Tester hele flowet fra klient til persistence for at sikre business-funktionalitet. Tungere og køres typisk sjældnere.

Slide 2: Struktur i semesterprojekt

Praktisk strategi i et multi-service projekt:

  • Hver service ejer sine unit tests (kør ofte lokalt)
  • Integration tests køres i CI (brug test-DB eller ephemeral containers)
  • E2E tests kører i trimmed Docker Compose eller testmiljø

Eksempler i repo: Python pytest fixtures i CatalogMicroService/tests, xUnit i eShopOnWeb-main/.../tests/UnitTests, Jest for NestJS.

Slide 4: Hvad er Message Transformation?

Message Transformation ændrer et message-format for at gøre det kompatibelt mellem systemer. Typiske transformationer:

  • Feltnavn konvertering (camelCase ↔ snake_case)
  • Schema-opgradering (v1 → v2)
  • Berigelse eller reduktion af payload

I eShopOnWeb kan OrderCreatedEvent have interne felter producer-side, men gateway eller transformer fjerner/tilføjer felter inden forbruger-modtagelse.

Slide 5: Hvor placere transformation?

  • Producer-side: Producer sender consumer-friendly format (centraliseret ansvar).
  • Broker-side / middleware: Gateway/transformation-service ændrer messages mellem exchanges.
  • Consumer-side: Consumer transformerer lokalt (fleksibelt men dupliceret logik).

Valg afhænger af ownership, performance og hvor ofte skemaer ændrer sig.

Slide 6: Teststrategier for messaging

  1. Unit tests: Test transformation-funktioner isoleret (f.eks. TransformV1ToV2()).
  2. Integration tests: Kør ephemeral RabbitMQ (docker) og verificer publish/consume og transformation.
  3. Contract tests: Consumer-driven contracts (Pact) sikrer kompatibilitet mellem producent og forbruger.
  4. E2E: Kør hele flow (API → publish → consume → DB) og valider end-state.

Slide 7: Eksempeltest — Messaging integration (pseudo)

# pseudo pytest
 def test_order_event_transformation(rabbitmq_container):
     publish(queue='orders.in', body=ORDER_V1_JSON)
     msg = consume(queue='orders.out', timeout=2)
     assert msg['amount'] == 1000
     assert 'internal_flag' not in msg  # removed by transformation

Flow: start ephemeral broker → publish → transform → consume → assert

Slide 8: Test automation & CI

Praksis:

  • Unit tests: Kør lokalt og i pre-commit
  • Integration tests: Kør i CI med containerized dependencies
  • E2E: Kør nightly eller som gating for store merges
  • Contract tests: Kør i både consumer- og producer-repos
# Eksempelkørsel i CI
 python -m venv venv
 .\venv\Scripts\activate
 pip install -r requirements.txt
 pytest

 dotnet test ./eShopOnWeb-main/eShopOnWeb-main/tests/UnitTests/UnitTests.csproj

Slide 9: Opsummering & Best Practices

  • Unit tests for correctness (hurtige)
  • Integration tests for contracts og transformations
  • E2E for kritiske business flows
  • Brug contract testing (Pact) for kompatibilitet
  • Test messaging med ephemeral brokers (docker / Testcontainers) og DLQ-validering
