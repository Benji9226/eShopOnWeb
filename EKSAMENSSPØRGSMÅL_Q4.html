Build- og Deployment-processer i Microservices & Systemintegration

Varighed: 10–15 minutter
Teknologier brugt i projektet: RabbitMQ, GitHub Actions, Docker

1. Introduktion: Microservices vs. Monolit

Før vi ser på build og deployment, er det vigtigt at forstå forskellen mellem monolitisk arkitektur og microservices.

  • Monolit: Hele systemet bygges og deployes som én samlet applikation.
  • Microservices: Systemet består af mange små, selvstændige services med hver deres kodebase, build-proces og deployment.
Eksempel:
En webshop kan opdeles i services som Order Service, User Service, Payment Service og Inventory Service, der alle deployes uafhængigt af hinanden.

2. Build-processen i Microservices

I microservices bygger hver service sin egen pipeline. Dette gør udviklingen hurtigere og mere fleksibel.

  • Kode pushes til GitHub.
  • CI-pipeline kører tests og bygger artefaktet.
  • Service pakkes som et Docker container image.
  • Image pushes til container registry.
Eksempel fra projektet:
GitHub Actions bygger automatisk Docker-images for hver service, når der pushes til main-branch.

3. Deployment-processen i Microservices

Deployment håndteres normalt service for service, og nye versioner kan rulles ud uden at påvirke resten af systemet.

Typiske elementer i en deployment-pipeline:

  • Container registry → Deployment miljø
  • Automatiseret deployment via scripts eller CI/CD
  • Orchestration (fx Kubernetes – hvis anvendt)
Eksempel fra projektet:
Docker containers startes og opdateres individuelt, så hver service kan deployes uden nedetid for resten af platformen.

4. Hvordan adskiller det sig fra en Monolit?

  • Monolit: Ét stort build → Ét stort deployment. Alt skal med hver gang.
  • Microservices: Mange små builds → Mange små deployments. Kun den ændrede service skal deployes.
Eks: Hvis du kun ændrer i Payment Service, skal du ikke genudrulle hele webshoppen – kun den service.

5. Systemintegration i Microservices

Microservices skal ofte kommunikere med hinanden. Dette kan gøres på flere måder:

5.1 Pipes and Filters

Pipes and Filters er et integrationsmønster hvor data sendes gennem en kæde af processer (filters). Hver filter udfører en lille opgave.

  • Filters = små funktioner/services der transformerer data.
  • Pipes = forbindelser mellem disse steps.
Eksempel:
En ordre gennemløber flere steps: Validering → Betaling → Lageropdatering → Forsendelse.
Hver step håndteres af en separat service.

5.2 Asynkron Messaging

Microservices kommunikerer ofte via asynkrone beskeder, så de ikke behøver at vente på hinanden.

  • Services sender events til et message broker-system.
  • Andre services lytter og reagerer på events.
  • Gør systemet mere robust og skalerbart.
Eksempel fra projektet (RabbitMQ):
Når Order Service opretter en ny ordre, sender den en besked til RabbitMQ. Inventory Service og Payment Service kan så lytte på denne besked og reagere uden direkte API-kald.

6. Hvorfor bruge Asynkron Messaging?

  • Microservices bliver løsere koblet – de kender ikke hinandens detaljer.
  • Der kan bygges workflows på tværs af services uden central koordination.
  • Fejltolerance: Hvis en service er nede, ligger beskeden i køen, indtil den er oppe igen.
Eksempel:
Hvis Payment Service er nede, går ordren ikke tabt. RabbitMQ gemmer beskeden, og service kan behandle den senere.

7. Opsummering

  • Microservices bygges og deployes uafhængigt – typisk via CI/CD som GitHub Actions.
  • Docker containers bruges som standard til packaging og deployment.
  • Systemintegration sker typisk gennem:
    • Pipes and Filters – sekventielle processer
    • Asynkron messaging – RabbitMQ som message broker
  • Resultatet er fleksible, skalerbare og robuste systemer.
